### 2.4 D-004 强提醒十分钟自动结束

- **编号**：D-004。
- **上下文位置**：`AlarmAlertService` 的铃声和振动无限循环；`AlarmActivity` 长期持有 `FLAG_KEEP_SCREEN_ON`；当前没有自动结束机制。
- **事项**：提醒开始十分钟后停止声音和振动、关闭对应全屏页，并停止主动保亮。
- **风险等级**：中。涉及 Service 与 Activity 两个生命周期；旧计时器误关新提醒会导致漏提醒。
- **候选方案**：只在 Activity 计时；只在 Service 计时；Service 作为事实源并通知 Activity，Activity 保留页面级兜底计时。
- **评估依据**：Activity 可能被系统拦截、销毁或复用，不能负责声音和振动；Service 能统一结束媒体，但不能直接安全持有 Activity 引用。当前已有 `AlarmAlertInstanceKey`，可隔离 `alarmId + kind + occurrenceTime`。
- **结论**：采用第三种方案。Service 为唯一强提醒会话事实源；每次新实例取消旧计时并重置十分钟；超时前校验实例完全相同，结束媒体和前台状态、保留静音通知、发送应用内显式关闭广播。Activity 仅关闭匹配实例，清除保亮标志，并保留独立兜底计时防止 Service 提前终止后页面常亮。
- **执行动作**：新增十分钟常量、实例匹配策略、Service 定时任务、Activity 非导出广播接收和兜底任务；补充策略及源码契约测试。
- **验证证据**：新增 4 个回归测试；v1.7 全量 JVM 测试 24 个类、83/83 通过；`compileDebugAndroidTestKotlin`、`lintDebug` 和 `assembleRelease` 通过；Lint 为 0 error、59 warnings、3 hints。
- **偏差与遗留风险**：普通第三方 App 不应申请设备管理权限强制关屏；本次语义是撤销 App 的保亮行为，最终熄屏时机仍服从 Android/HyperOS 系统策略。
- **回滚条件**：若真机发现超时误关新实例，立即回滚自动结束功能；保留实例日志后重新定位，不降级为无实例校验的全局停止。

### 2.7 D-007 强提醒诊断体系（P0/P1）

- **编号**：D-007。
- **上下文位置**：v1.7 已具备自动结束保护，但真机仍可能出现“解锁后横幅、到点无全屏、熄屏不稳定”等系统与厂商策略相关现象；当前仅有散落 Logcat，无法由用户离线保存和关联一次提醒。
- **事项**：建立不改变提醒策略的应用侧黑匣子、解析和用户可控导出能力。
- **风险等级**：中。诊断若阻塞闹钟接收器、前台服务或 UI，会扩大提醒故障面；日志若包含标题/备注会造成隐私泄露。
- **候选方案**：继续依赖 Logcat；把诊断表写入 Room；写入应用私有追加式 JSONL，并在设置页提供增强采集和导出。
- **评估依据**：普通第三方 App 不能读取系统 Logcat；Room 迁移会与核心提醒库耦合并增加一次性风险；JSONL 可独立限额、故障隔离、直接导出，适合小体量离线 App。
- **结论**：采用第三种方案。P0 记录调度→Receiver→前台服务→通知→全屏请求→Activity→十分钟计时器的实例级事件；P1 提供诊断中心、24 小时增强诊断、时间线解析、主动 ZIP 导出与清除。`traceId` 只由 `reminderId + alarmId + kind + occurrenceTime` 构成，禁止持久化标题、备注、异常原文和 URI。日志写入失败必须吞掉，不能影响提醒链路。
- **执行动作**：新增 `diagnostics/core` 纯解析层和 `diagnostics/platform` 私有存储层；接入四个提醒关键节点；设置页新增诊断入口；注册仅导出缓存 ZIP 的 `FileProvider`；版本升级为 v1.8（code 9）。
- **验证证据**：JDK 17 下 `compileDebugKotlin`、87 个 JVM 测试、`compileDebugAndroidTestKotlin`、单线程 `lintDebug` 和单线程 `assembleRelease` 均以退出码 0 完成。首次把 Lint 与 Release 并发组合执行时，Lint 读取到被 Release 重建的 KAPT 临时 stub 而报 Android Lint 内部异常；串行单独执行后通过，未发现本次代码规则错误。
- **偏差与遗留风险**：应用事件只能确认本应用已请求或已进入自身生命周期；不能确认 SystemUI 最终是否以全屏、横幅或锁屏样式展示。增强模式仅增加快照密度，24 小时到期后自动停止；基础故障链路仍保留。
- **回滚条件**：诊断 I/O 造成提醒延迟、前台服务异常或隐私字段泄露时，整体回滚 D-007；不回滚 v1.7 的十分钟自动结束保护。

### 2.8 D-008 Android 16 BAL 根因修复

- **编号**：D-008。
- **上下文位置**：红米 K80 Pro（Android 16、HyperOS）已连接；用户导出的 `reminder-diagnostics-1786448421205.zip` 与 2026-08-11 20:00、20:05 系统 Logcat 可关联同一提醒实例。
- **事项**：修复后台时提前/到点仅留下通知、没有页面的根因；同时修正诊断误报、锁屏展示方式和保留通知进入编辑页的问题。
- **根因证据**：ZIP 中两次实例均记录 `soundRequested=false`、`vibrateRequested=false`，说明该保存提醒当前选择仅视觉通知；`PLAYBACK_STARTED` 却写为 `started` 是诊断语义错误。`ActivityTaskManager` 两次明确输出 `Background activity launch blocked`，调用方为 `com.reminder.local` 前台服务，目标为 `AlarmActivity`；旧代码在通知前 `wakeScreen()`，再自行 `PendingIntent.send()` 拉起页面。通知、全屏通知、精确闹钟和前台服务权限已在设备侧允许。
- **风险等级**：高。继续使用自拉起路径在 targetSdk 36 上可稳定失败；把 `send()` 未抛异常写成成功会误导后续修复；自动覆盖已保存的声音/震动选择会侵犯用户配置。
- **候选方案**：保留自拉起并继续调整 BAL options；先 WakeLock 再交给通知；只发布 FullScreenIntent，由系统通知链路决定 Activity，锁屏页面仅 `showWhenLocked/turnScreenOn` 展示。
- **评估依据**：系统日志已证明第一种被拦截；第二种会提前将锁屏变为交互状态并增加横幅降级概率；第三种符合 Android 的安全模型，仍保留声音、震动和高优先级通知作为全屏未显示时的可感知降级。
- **结论**：采用第三种。删除 Service 与 Receiver 兜底中的后台 `PendingIntent.send()`、删除通知前 Screen WakeLock；保留系统 FullScreenIntent。区分全屏和通知点击的 PendingIntent 来源，Activity 记录来源；不自动改写既有声音/震动开关，仅在两者关闭时展示明确 UI 提示。保留通知新旧入口均进入列表而不是编辑页。
- **执行动作**：版本升级为 v1.9（code 10）；新增诊断来源和回归测试；更新 PRD、架构、诊断、交接、测试和交付文档；覆盖安装到目标手机，不清除数据。
- **验证证据**：91 个 JVM 测试、`compileDebugAndroidTestKotlin`、`lintDebug`（0 error、59 warnings、3 hints）和 `assembleRelease` 通过；APK 元数据为 `1.9 (10)`、v2 签名有效、SHA-256 为 `0a8879d56ba25d749c2a1b88b7e648162dba27ef5924a93a1ef4a9200c1b6f33`；ADB 覆盖安装成功并读回 `versionName=1.9`。手机在安装后处于 AOD/锁屏，尚未执行新的真实定时触发。
- **偏差与遗留风险**：Android 已解锁且正在使用时，SystemUI 仍可能展示 Heads-up 横幅，普通 App 不可强制全屏；现有保存提醒的声音和震动仍为关闭，需在编辑页主动打开后再验声音和震动。
- **回滚条件**：真实锁屏定时触发中若通知与媒体都未出现，保留新版 ZIP 与 SystemUI Logcat 后回滚 D-008；不得恢复已确认被 BAL 拦截的后台自拉起实现。

### 2.9 D-009 并发提醒接管诊断补强

### 2.12 D-012 回收站、列表治理与范围收敛

- **编号**：D-012。
- **上下文位置**：用户要求一次性交付“已删除可恢复”、500 字标题、四行省略、紧凑首页与微信式多选整理；同时明确移除所有语音备忘、音轨、转写、智能语音与音频备份计划。
- **事项**：在不重构提醒调度架构的前提下补齐提醒 CRUD 生命周期和首页管理效率。
- **风险等级**：高。物理删除会造成误删不可恢复；把排序写进提醒时间会导致漏提醒/重复提醒；把语音能力混入本版会扩大权限、存储和测试范围。
- **候选方案**：继续物理删除；单独建立复杂回收站表；在现有 `reminders` 增加软删除状态；只做逐条拖拽；多选批量整理与拖拽并存。
- **评估依据**：个人提醒规模通常只有十几至几十条，现有单表和 Room 足以覆盖；用户高频动作是批量把新事项移到顶部，精确排列才需要拖拽。独立回收站表会增加迁移、恢复和调度一致性分支，无实际收益。
- **结论**：采用 `DELETED + deletedAt + statusBeforeDelete` 三字段的软删除；正常查询、分类计数和重调度统一排除 `DELETED`。排序采用微信式多选置顶/置底/删除为主、长按把手拖拽为辅，以 `manualSortOrder` 独立持久化；只允许在“全部”下整理。标题上限为 500，首页最多 4 行省略。全部语音相关能力明确不做。
- **执行动作**：Room 升级 v5 并添加 v4→v5 迁移；新增恢复、永久删除、排序用例和“已删除”页面；首页进入整理模式后切换手动排序，新增事项取当前最大排序号后追加；编辑页采用紧凑布局并把提前、重复字段移到提醒时间下方；更新 PRD、交接、测试和 APK 文档。
- **验证证据**：v1.13 的 JVM 106 个测试通过、失败 0、错误 0；Room v5 schema 已生成，新增 v4→v5 仪器迁移用例。后续 v1.14 结果不继承本条历史结论。
- **偏差与遗留风险**：精细拖拽以当前可见列表为边界，大跨度移动优先使用批量置顶/置底；真实设备的四行截断密度、拖拽手势和迁移仍需验收。恢复历史过期单次提醒不会补发，恢复为 `EXPIRED`。
- **回滚条件**：若 v5 迁移、恢复后闹钟重建或排序持久化出现数据不一致，停止发布并回滚该提交；不得通过 destructive migration 清空用户提醒。

### 2.13 D-013 编辑页撤销/重做与紧凑操作栏

- **编号**：D-013。
- **上下文位置**：v1.13 编辑页只有顶部宽“保存”按钮和编辑态直接删除图标，没有表单修改历史；用户希望减少保存按钮占用并提供撤销、重做。
- **事项**：为新增/编辑页增加本次会话内的撤销、重做和紧凑保存操作，不改变提醒数据模型和保存后的业务状态。

- **结论**：采用整个表单的 ViewModel 内存历史，最多 50 个有效步骤；同一输入框的连续文字编辑合并为一次记录，新编辑会清空重做栈；保存成功后清空撤销/重做历史。顶部使用 RTL 兼容的撤销、重做图标和 40dp 对勾保存按钮；编辑态删除移入“更多操作”菜单。

- **验证证据**：v1.14 JVM 111/111 通过；`compileDebugAndroidTestKotlin` 通过；Lint 为 0 error、67 warnings、4 hints；Release `1.14 (15)` 构建成功；APK v2 签名有效、SHA-256 为 `94f7eb3e0ae525b874608e6b017bb757895f641f567e9e5bfdf54d8badfbdfb7`。真机的图标可识别性、单手点击、撤销/重做触摸行为仍需设备验收。
