# 强提醒诊断与日志体系

> 状态：v1.12 P0/P1 已验证；新增应用悬浮层可确认展示证据
> 更新时间：2026-08-12

## 目标与边界

目标不是再修一次现象，而是为 Reminder App 建立一套“没有连接电脑也能持续采证”的诊断与日志基础设施，让后续故障从猜测变成可还原、可定位、可验证，事后也能完整还原为什么没有全屏、为什么 DUE 被降级、为什么熄屏表现不一致，以及为什么自动结束没有生效。

面向“到点未全屏、解锁后仅横幅、熄屏表现不一致、十分钟未结束”等问题，保留可按一次提醒实例关联的应用侧证据。诊断层本身不改变提醒结果；写入失败、存储满或导出失败都不得阻断提醒。

普通应用不能读取系统 Logcat，也不能确认 SystemUI 的最终展示样式。因此诊断结论分为：

| 结论等级 | 含义                                                                                   |
| -------- | -------------------------------------------------------------------------------------- |
| 已确认   | 应用侧方法失败，或 `AlarmActivity` 已进入自身 `onResume/onWindowFocusChanged` 生命周期 |
| 高可能   | 应用已发通知并请求全屏，但未得到 Activity 生命周期证据；可能被系统或厂商策略压制       |
| 证据不足 | 仅有计划登记时表示尚未到点；到点后链路前段缺失才需查看权限快照和下一次复现             |

## 项目专属诊断体系：Reminder Black Box

业务层：AlarmScheduler / Receiver / Service / Activity / 用户操作
  ↓ 写入不可变事件
诊断核心：实例关联、状态机、错误分类、根因推断、脱敏
  ↓ 通过接口
平台层：私有文件持久化、系统状态快照、导出 ZIP、诊断中心 UI

核心原则：
每个 ADVANCE、DUE、SNOOZE 都有唯一 alertInstanceId。
事件不可修改，按时间线追加。
诊断存储独立于 Room 业务库，避免“数据库异常时诊断也不可用”。
默认保存最小黑匣子；用户可开启 24 小时增强诊断。
不记录标题、备注、通知正文、账号、路径、Token 或完整异常原文。
不自动上传；仅用户主动导出。

## 事件模型

- 实例关联：`reminderId + alarmId + kind + occurrenceTime` 生成 `traceId`；`ADVANCE`、`DUE`、`SNOOZE` 不混合。
- 关键链路：调度 → Receiver → 前台服务 → 声音/振动 → 通知 → 全屏请求 → Activity 生命周期 → 十分钟计时器 → 关闭。
- 数据最小化：不写入标题、备注、URI、异常正文或堆栈；字段自动截断。
- 存储：应用私有 `files/diagnostics/events.jsonl`，追加写入，2 MiB 自动轮转一份历史文件；列表、清除和 ZIP 导出均覆盖两段文件；不使用业务 Room，数据库维持 v4。

## P0：基础黑匣子

- 总是记录核心链路事件和错误结果。
- 到达 Receiver、前台服务失败、全屏请求失败、十分钟到期时写入基础系统快照：精确闹钟/通知/全屏权限、锁屏与交互状态、省电限制、音量等。
- 事件写入在独立线程执行并捕获失败；诊断不得反向依赖提醒业务。

## P1：用户可操作诊断

- 设置 → 诊断与排障：查看最近链路及解析结论。
- 增强诊断：用户主动开启，24 小时自动关闭；在所有关键检查点增加系统快照密度。
- 导出：仅用户主动操作时，生成缓存 ZIP 并用临时 `FileProvider` 授权分享；不需要存储权限，不联网。
- 清除：仅删除私有诊断记录，绝不影响提醒数据。

## v1.9-v1.11 真机取证与诊断补强

2026-08-11 导出的 ZIP 已足以还原“应用是否收到闹钟、是否启动前台服务、当前提醒是否请求声音/震动、是否发布通知、页面是否进入生命周期”。它不能单独证明 SystemUI 最终以全屏、横幅或锁屏卡片呈现，仍需同时保留系统日志和录屏。

本次 ZIP 与红米系统日志确认了三个事实：保留提醒的 `soundRequested=false`、`vibrateRequested=false`，因此没有声音和震动是已保存配置而非媒体启动失败；v1.8 将“不需要播放”误写为 `playback_started=started`；20:00 与 20:05 的自拉起 `AlarmActivity` 被 Android 16 `Background activity launch blocked` 拦截。

v1.9 的事件规则如下：

- `playback_started=not_requested` 明确表示用户关闭了声音和震动；只有实际媒介启动才为 `started`。
- `full_screen_requested=notification_manager_delivery` 只表示应用把 FullScreenIntent 交给系统通知；不等同于全屏已显示。
- `activity_created`、`activity_new_intent`、`activity_resumed`、`activity_focused` 写入 `launchSource`：`notification_full_screen`、`alert_notification`、`alarm_clock` 或 `unknown`。
- 解析器只在 `notification_full_screen + Activity 生命周期` 同时存在时确认系统已把提醒页带入前台；用户点击通知和旧日志不会被误判为自动全屏。
- 诊断卡片把孤立的 `alarm_scheduled` 作为调度证据，不与同实例的提醒链路混写；下一轮可继续增加 `scheduleKind`、计划/实际延迟和 NotificationManager 反馈，但不记录标题、备注或系统日志正文。

v1.9 的 21:00 真机触发已确认：锁屏 ADVANCE 由 `com.android.systemui:full_screen_intent` 唤醒，并让 `AlarmActivity` 成为前台窗口。21:05 DUE 已到达 Receiver、前台服务和带 FullScreenIntent 的正式通知；测试过程中 21:10 另一条提醒接管了单一强提醒会话，随后又收到停止操作，因此不能把旧通知变为静音误判为 DUE 的十分钟超时。

v1.10 为此补充：

- `alert_preempted` 记录旧实例被哪一个 `alarmId/kind/occurrenceTime` 的后续提醒接管；解析器明确标为并发切换，不再提示“自动结束”。
- `alert_closed.source` 区分 `alarm_page_close`、`alarm_page_snooze`、`alarm_page_done`、通知操作关闭、通知划掉、通知稍后和通知完成；不再把所有停止都笼统归为服务停止。
- 这些字段只保存内部 ID、kind、时间和来源，不记录标题、备注或系统日志正文。新的单提醒验收必须避免第二条提醒和人工操作干扰。

v1.11 根据 2026-08-12 的现场复盘补充：

- `alarm_scheduled` 且没有 `receiver_entered` 时，解析结论为“提醒已登记，尚未收到到点接收器事件”，不再错误提示“链路中断”。因此截图中连续 `alarm_scheduled` 只说明用户保存或重建了未来计划，不能用来证明闹钟未触发。
- `scheduleSnooze()` 现在与 DUE/ADVANCE 一样记录独立 `SNOOZE` trace 的注册成功或失败、`triggerAt`、requestCode 与来源；到点后现有 Receiver、Service、通知和 Activity 事件会自动接续同一 trace。
- 8 月 12 日真机的 DUE/ADVANCE 均已进入 Receiver 和前台服务，且通知含 `fullScreenIntent`。v1.11 的 20:12 DUE 同时获得 SystemUI `pinned Heads-up` 证据、没有 Activity 生命周期，直接证明“应用投递成功但解锁态系统选择横幅”。被测提醒的 `soundRequested=false`、`vibrateRequested=false` 是保存配置，不是媒体被系统阻断。
- 应用仍无法读取 SystemUI 的最终“全屏或横幅”决策。Android 官方定义：设备已解锁且用户正在使用时，SystemUI 以 expanded Heads-up 替代 FullScreenIntent；应用的诊断只能确认请求与自身 Activity 生命周期，不能伪造系统展示结论。

v1.12 根据最新诊断包和用户授权补充：

- 新诊断包包含一条完整旧版 SNOOZE：21:36:17 点击稍后，21:46:17 到达 Receiver，约十分钟后准时触发；`soundStarted=true`、`vibrationStarted=true`。缺失的是解锁页面，不是稍后调度。
- 新增 `overlay_requested`、`overlay_shown`、`overlay_failed`、`overlay_dismissed`；快照增加 `overlayAllowed`。`overlay_shown` 表示 `WindowManager.addView()` 已成功，置信度高于 `full_screen_requested`，但仍需截图或 `dumpsys window`确认厂商最终画面。
- 专用真机测试已形成三层证据：事件记录 `overlay_shown`；`dumpsys window` 记录 `APPLICATION_OVERLAY`、Surface ready 和完整尺寸；真机截图显示实际整页。测试清理后记录 `overlay_dismissed`。
- 20:55 的真实 DUE 使用同一路由再次成功，排除“只有测试入口能显示”的假阳性。
- 21:03:16 从真实 DUE 点击稍后，诊断记录独立 SNOOZE 的 `alarm_scheduled`；21:13:16 准时接续 `receiver_entered → foreground_service_started → overlay_shown → playback_started`，声音和震动均成功，证明新版稍后提醒不是只登记不触发，也不再因解锁而只显示横幅。

## 复现与取证流程

1. 进入诊断中心，开启增强诊断。
2. 记录测试提醒的计划时间；分别覆盖解锁、熄屏、锁屏和 ADVANCE→DUE。
3. 发生现象后回到诊断中心刷新并导出 ZIP；同步记录系统版本、权限状态、录屏和实际现象。
4. 若仅显示“提醒已登记”，先比较当前时间和 `triggerAt`，未到点时不做故障判断；到点后再检查 Receiver。
5. 锁屏链路若结论为“高可能”，优先检查全屏通知权限、通知渠道锁屏显示和厂商策略；不要把“全屏请求成功”误判为“系统已显示全屏”。
6. 解锁链路必须检查 `overlayAllowed → overlay_requested → overlay_shown → overlay_dismissed`；`permission_missing` 直接指向权限入口，`add_view_failed` 再结合设备日志定位 WindowManager/OEM 拒绝。

## 维护约束

- 新增、重命名提醒枚举或改变全屏策略时，同步增加事件和解析规则。
- 诊断字段先经过脱敏；禁止为排障临时写入标题、备注或完整异常堆栈。
- 诊断出现异常时只记录自身最小错误，业务链路继续执行。
