## 第一章 架构分层

```text
UI / Compose
  ↓
ViewModel
  ↓
UseCase / domain policy
  ↓
Repository interface
  ↓
Room DAO / DataStore / AlarmManager adapter
```

- 上层只依赖下层；UI 不直接访问 DAO 或 AlarmManager。
- 业务校验、重复计算和实例隔离放在领域层，Android 组件只负责系统适配。
- 文案、默认配置和逻辑分别维护；不为个人离线应用引入网络、微服务或无实际变化点的抽象。

## 第二章 提醒生命周期

```text
AlarmScheduler → AlarmManager → AlarmReceiver → AlarmAlertService
                                      ├─ 循环铃声与振动
                                      ├─ 锁屏：高优先级通知与 SystemUI FullScreenIntent
                                      ├─ 解锁：TYPE_APPLICATION_OVERLAY 强提醒页
                                      ├─ 实例级十分钟自动结束
                                      └─ 通知中心记录与操作入口
```

- `ADVANCE`、`DUE`、`SNOOZE` 使用独立 kind 和 PendingIntent 身份；只有 `DUE` 推进重复周期。
- 所有操作和超时必须携带并校验 `reminderId + alarmId + kind + occurrenceTime`。
- Service 是强提醒会话事实源；Activity 不负责决定媒体是否继续。
- 新实例到来时取消旧计时并重新计满十分钟；旧 Runnable 只能结束完全匹配的实例。
- 单一强提醒会话被后续提醒接管时，旧实例保留静音通知，并写入 `alert_preempted`；停止操作必须写入具体来源，不能与自动超时混淆。
- Activity 接收应用内非导出自动关闭广播并再次校验实例；页面级计时只作为 Service 异常退出后的保亮兜底。
- 自动结束不标记业务事项完成，默认保留静音通知。
- 后台强提醒不得由 App 自行 `PendingIntent.send()` 拉起 Activity；该路径在 Android 16 会被 BAL 拦截。通知发布前不得主动唤醒屏幕，避免把锁屏场景误变为已交互场景。
- `AlarmActivity` 只使用 `setShowWhenLocked` 与 `setTurnScreenOn` 覆盖锁屏，不请求解除 Keyguard；通知点击、系统全屏和闹钟图标必须带可诊断的来源标识。
- 解锁且交互状态使用纯策略 `AlarmVisualRoutePolicy` 选择应用悬浮层；窗口由 Service 创建和销毁，不依赖 Activity 生命周期。悬浮层显示成功后不得再绑定 FullScreenIntent，避免同一实例同时出现悬浮页和横幅。
- 悬浮页的关闭、稍后、完成和十分钟超时复用 Service 的实例隔离与 Receiver 操作链路；Service 销毁、提醒接管或实例切换必须同步移除窗口。

## 第三章 数据与一致性

- Room 当前版本为 v5，禁止 `fallbackToDestructiveMigration`。
- 回收站使用同表软删除：`DELETED`、`deletedAt`、`statusBeforeDelete`；正常列表、分类统计和待调度查询必须排除 `DELETED`，永久删除只接受该状态。
- `manualSortOrder` 与提醒时间分离；手动顺序只用于未完成列表，新增事项追加到现有最大序号后，排序批量写入必须在 Room 事务中完成。
- `alarmId` 必须唯一；迁移脏数据时使用确定性、一一映射且不超出 `Int` 范围的算法。
- `triggerTime` 是重复模板，`nextTriggerTime` 是下一次实际时间；不得混用。
- Receiver 推进重复时按 occurrence 条件更新，防止重复广播二次推进。
- Room 与 AlarmManager 不是同一事务。校验应先于取消旧闹钟；失败时恢复旧状态、撤销新状态或记录明确错误。
- 开机、应用更新、权限恢复和用户打开 App 可触发闹钟重建；单条失败必须隔离。

Room 字段变化必须同步检查 Model、Entity、Converter、Mapper、DAO、Repository、UseCase、ViewModel、UI、Migration、Schema 和测试。枚举名是持久化协议；重命名或删除必须配套 Migration，Converter 默认值只是损坏数据兜底。

编辑页撤销/重做属于 ViewModel 层的短生命周期 UI 状态，不进入 Room；历史最多保留 50 个有效步骤，同一输入框连续文字编辑合并记录，保存后清空。

## 第四章 变化点与工程规则

| 变化点 | 扩展位置 | 不变量 |
|---|---|---|
| 重复规则 | `RepeatType` 与 `RepeatCalculator` | 设备时区、模板时间与下一次时间分离 |
| 提前规则 | `AdvanceReminderType` 与计算器 | 不推进正式周期，不覆盖 DUE |
| 提醒媒介 | Service 与通知策略 | 实例隔离、失败降级、用户开关生效 |
| Android 版本 | 视觉路由策略、窗口适配与权限工具 | 锁屏不绕过 BAL；解锁悬浮层必须由用户显式授权 |
| Room 结构 | Migration 与 Schema | 不清库、可升级、测试可复现 |
| 回收站与排序 | Delete/Restore/Reorder UseCase、DAO 与 UI | 删除后不调度；恢复不补发过期单次；排序不改时间 |

- 精准修改，不顺手重构无关弃用 API。
- 日志记录内部 ID、kind、时间和状态，不记录标题、备注等用户内容。
- 诊断层只依赖 Android 平台与纯核心模型，不依赖 Room 业务表；写入和导出失败必须被隔离，不能改变闹钟和强提醒结果。
- 关键选型、风险、证据和回滚条件写入 [AI 自主决策记录](../04-开发文档/01-AI自主决策记录.md)。

## 第五章 测试与交付约束

- 修复先覆盖根因、边界和防回归；相关模块通过后再做全量测试、Lint 和 Release 构建。
- JVM、仪器测试源码编译、设备/模拟器仪器执行、APK 验签和目标真机验收是独立证据层。
- APK 使用 `ReminderApp-v<version>.apk` 命名；APK、keystore、密码、token 和 `local.properties` 不提交仓库。
- 真机未执行的场景必须明确写“待验证”，不能以源码推断替代设备结论。
