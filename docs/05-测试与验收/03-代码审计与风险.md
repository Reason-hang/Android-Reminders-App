## 审计结论

当前未发现阻断 Release 构建的代码错误。v1.6 以前确认的事件身份、重复推进、迁移和 Converter 问题保持修复；v1.7 新增实例级十分钟自动结束，解决铃声、振动和全屏页可无限持续的问题。目标设备行为仍需真机采证。

v1.9 使用红米系统日志确认并移除了 Android 16 BAL 拦截路径：后台前台服务不再自行启动 `AlarmActivity`，只由系统对通知的 FullScreenIntent 投递；也不再在通知前用 WakeLock 改变屏幕交互状态。锁屏 ADVANCE 已由真机确认进入 `AlarmActivity`。v1.10 已确认 DUE/ADVANCE 投递。v1.11 修正未来计划被误报为提醒链路中断，并补齐 SNOOZE 调度证据。

## 已修复问题

| 范围 | 根因 | 当前修复 |
|---|---|---|
| 强提醒超时 | 铃声和振动无限循环，Activity 持有 `FLAG_KEEP_SCREEN_ON` 且无定时退出 | Service 管理十分钟实例计时；超时停止媒体与前台状态，通知 Activity 清除保亮并关闭 |
| 超时并发 | 旧 ADVANCE 或旧提醒的计时器可能误关新实例 | 超时按 `alarmId + kind + occurrenceTime` 完全匹配；新实例取消旧计时 |
| DUE 语义 | 提前提醒未关闭时，正式到点需要再次强提醒 | 同一 `alarmId` 的新 occurrence 重启播放和投递链路 |
| 后台全屏 | Service 自行 `PendingIntent.send()` 在 Android 16 被 BAL 拦截，页面不出现 | 删除 Service 与备用通知的自拉起；系统通知成为唯一 FullScreenIntent 投递者 |
| 诊断语义 | 静音配置被写为 `playback_started=started`；Activity 生命周期不区分来源 | 记录请求/实际启动与 `launchSource`；旧记录只标为证据不足 |
| 并发诊断 | 单一强提醒服务被后续提醒接管或停止时，旧时间线无法说明原因 | 记录 `alert_preempted` 和具体停止来源，解析器不再归因到自动超时 |
| 通知路由 | 保留通知点击直接进入编辑页 | 新旧入口均只进入提醒列表 |
| Room 迁移 | 历史脏 `alarmId` 可能使唯一索引失败 | v3→v4 按确定顺序分配连续负值，保留 Schema 和迁移测试 |
| 枚举读取 | 未知持久化文本会使查询 Flow 异常 | Converter 使用保守默认值；枚举改名必须配套 Migration |
| 时区和校验 | 工作日固定时区、长度限制仅在 UI | 统一设备时区，标题和备注限制下沉 UseCase |

## 平台行为边界

- Android 在锁屏时可展示 Full-screen Intent；设备已解锁且用户正在操作时通常展示 Heads-up 横幅。
- 代码只请求 Full-screen Intent；最终结果仍受全屏通知权限、通知渠道、SystemUI 和 HyperOS 策略控制。
- 因此“解锁后必须百分之百全屏”不是普通第三方 App 可稳定保证的验收条件。
- 屏幕关闭不等于 Keyguard 已锁定；真机测试必须分别记录两种状态。
- 自动结束撤销 App 保亮，不使用设备管理或系统签名权限强制关屏。
