## 二、总体结论

1. **v1.14 闪退根因已在 v1.16 做了边界性修复。** `statusBeforeDelete` 是可空历史字段，不能与必填 `status` 共用一个需要同时表达两种空值契约的 Room 枚举 Converter。当前 `status` 继续走必填 Converter，`statusBeforeDelete` 以可空原始 TEXT 保存，在 Mapper 层安全解析；NULL 或未知文本不会让列表查询抛异常。
2. **恢复提醒和撤销完成的部分闹钟注册残留已修复。** `AlarmSchedulerImpl.scheduleExact()` 是分步注册 DUE/ADVANCE，第二步失败时可能已经留下第一步；两个调用方现在在调度异常路径执行取消补偿，数据库仍保持原状态。
3. **当前静态审计未发现新的 P0 代码阻断项。** 本次修复没有引入数据库版本变化，Room schema 仍为 v6，未使用 destructive migration。
4. **真机风险仍未闭环。** 当前没有本次 v1.16 的 ADB/红米执行证据，解锁横幅、锁屏全屏、通知渠道、HyperOS 后台策略、覆盖升级冷启动和十分钟实际熄屏必须按真机清单验证。

## 三、审计发现与修复

### N1（P0，已修复）：可空 `statusBeforeDelete` 进入非空 Converter 导致冷启动闪退

- **证据**：用户提供的 v1.14 栈命中 `Converters.stringToStatus`，Room 生成的 `ReminderDao_Impl.getAllPending()` 在读取 `SELECT *` 时把正常记录的 SQL NULL 传入 Kotlin 非空参数。
- **根因**：回收站恢复前状态允许 NULL，但原 Entity/Converter 设计把它当作 `ReminderStatus?` 与主状态共用转换协议；Kotlin 在方法体前就可能抛 `NullPointerException`，默认值逻辑无法执行。
- **当前修复**：`ReminderEntity.statusBeforeDelete` 改为 `String?`（`app/src/main/java/com/reminder/local/data/db/entity/ReminderEntity.kt:42-43`）；`Reminder.status` 使用唯一的必填枚举 Converter（`Converters.kt:11-19`）；`Mappers.kt:30,54,57-58` 负责 NULL、合法值和未知值的安全转换。数据库列仍为 nullable TEXT，因此 schema v6 无变化、无需新增迁移。
- **防回归**：`ConvertersTest` 覆盖 NULL/未知主状态默认值；`MappersTest` 覆盖 NULL、合法值和未知回收站状态；现有 DAO/迁移测试源码继续编译。

### N2（P1，已修复）：Room Converter 可空性边界不应依赖 Kotlin 重载区分

- **证据**：尝试为同一枚举同时注册可空与非空 Converter 时，KAPT 报告 `Multiple functions define the same conversion`；这证明“依赖参数可空性拆两个同名转换协议”不是稳定方案。
- **根因**：Room 选择 TypeConverter 依据的是数据库类型和目标类型，不能把业务上两个不同字段的 NULL 语义安全地交给一组重叠 Converter。
- **当前修复**：稳定字段 `status` 保留 `ReminderStatus` 类型；仅对易损的回收站历史字段采用原始 TEXT + Mapper 转换，避免 Room 转换器冲突，也不改变 SQL schema。
- **验收**：全量 JVM、KAPT、Android 仪器测试源码和 Release 均通过。

### N3（P1，已修复）：分步注册闹钟失败会留下系统侧孤儿注册

- **调用链**：`RestoreReminderUseCase.invoke()` 在 `RecycleReminderUseCases.kt:44-61`、`CompleteReminderUseCase.markPending()` 在 `CompleteReminderUseCase.kt:100-117` 调用 `scheduleExact()`；调度器先注册 DUE，再按需注册 ADVANCE。
- **根因**：AlarmManager 与 Room 不构成跨系统事务。若 DUE 已注册而 ADVANCE 注册失败，原调用方只返回失败，未取消已注册实例，可能留下 stale system alarm；它通常不会造成数据丢失，但会造成错误的系统闹钟图标/后续无效广播和排障噪音。
- **当前修复**：调度异常时按同一提醒身份执行 `alarmScheduler.cancel(updated/restored)`；数据库不提交新的恢复/撤销状态。清理失败仍单独记录错误，不覆盖原调度异常。
- **防回归**：新增 `restoreScheduleFailureCancelsPartiallyRegisteredAlarm` 与 `undoCompletedReminderCleansPartiallyRegisteredAlarmOnScheduleFailure`，测试桩明确模拟“已写入一部分后抛错”。

### N4（P2，保留）：诊断文件轮转与导出缺少更强的 I/O 反馈

- `DiagnosticStore.rotateIfNeeded()` 忽略 `renameTo()` 返回值（`DiagnosticStore.kt:53-57`）；极端文件系统失败时可能无法按预期轮转。
- `DiagnosticsRepository.exportIntent()` 在用户点击导出时同步读取并压缩最多两段诊断文件（`DiagnosticsRepository.kt:32-53`）；当前上限较小，但仍可能在低端设备造成短暂 UI 阻塞。
- **当前决定**：本轮不改变提醒核心链路，不扩展诊断架构；后续可增加轮转失败事件、后台导出状态和临时文件清理测试。该项不是本次闪退或闹钟业务错误的直接根因。

### N5（P2，保留）：Release 使用 Debug 签名

Release 构建可验签，但签名证书为 Android Debug，不适合应用商店或长期正式分发。当前仅支持个人直装/测试；正式 keystore 由用户单独保管后再切换，避免把凭据提交仓库。

## 四、分层与安全检查

### 4.1 架构与一致性

- UI → ViewModel → UseCase → Repository → Room/系统适配的单向依赖保持；本次 Mapper 修复没有把 Android 依赖引入领域层。
- `triggerTime`、`nextTriggerTime`、`alarmId` 和 `manualSortOrder` 语义未改变；排序、回收站和 Converter 修复不改提醒时间。
- 调度失败补偿明确承认 Room 与 AlarmManager 非同一事务，避免“数据库已恢复但系统闹钟残留”的不一致。
- `ADVANCE`、`DUE`、`SNOOZE` 的实例身份和十分钟超时逻辑未被本次修复改动。

### 4.2 安全与隐私

- Manifest 未声明 `INTERNET`；未发现 WebView、动态代码执行、硬编码密钥、账号或远程数据链路。
- PendingIntent 使用 immutable；业务组件默认不导出；诊断文件保存在应用私有目录，仅用户主动导出。
- 日志和诊断不记录提醒标题、备注正文、Token 或完整用户路径。
- 悬浮窗仍是高影响特殊权限，只在真实强提醒会话创建并在关闭/超时/服务销毁时移除。
